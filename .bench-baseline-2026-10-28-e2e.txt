=== End-to-end floor (T2 warm/cold + T2-native), recorded 2026-10-28 ===

What this file is. The absolute floor the `e2e-gate` job of
.github/workflows/bench-gate.yml grades `cargo bench --bench compiler -- e2e_`
against, read with `--floor-prefix ''` (every row below is a full criterion id).
It is separate from .bench-baseline-2026-06-01-correctness.txt, which guards the
frontend (T1) budget and is unchanged. Tiers are defined in docs/benchmarking.md.

What was measured. The compiler is origin/main ecd8be99, i.e. BEFORE the
end-to-end speed work (runtime-object cache switch, tool-identity memo, native
front-end work). Each later item's gain shows up as a new floor in this file's
history, measured the same way. `mindc` built with
`--features "mlir-build std-surface cross-module-imports"`, release profile,
LLVM 20.1.8 (`mlir-opt`, `mlir-translate`, `clang`).

  - e2e_compile_shared/warm/<shape>: `mindc src --emit-shared out.so` with the
    runtime-object cache primed.
  - e2e_compile_shared/cold/<shape>: the same with a fresh, empty
    XDG_CACHE_HOME per run (and MINDC_RUNTIME_OBJ_CACHE=0).
  - e2e_native/<shape>: `mindc build --backend native src --out elf` from the
    repository root, on the pinned backend_native_bridge corpus; every output
    was byte-identical to its committed oracle ELF.

How. A wall-clock harness (perf_counter around one spawned process), 40 timed
runs per row after 2 untimed rounds, every row interleaved in a per-round
shuffled order in ONE session, pinned with taskset to 4 idle physical cores
(both SMT threads) of a Linux build host: Xeon E5-2699 v3 (Haswell-EP), 2 x 18
cores, SMT on, other unrelated jobs running on the other socket. The value on
each row is the MEDIAN, which is what criterion's bencher line reports and what
tools/bench_gate.py compares. Spread is given as p10/p90 beside each row.
The release mindc built from this commit and from origin/main are
byte-identical (same sha256), and both were timed in the same session as an
A/A control: their medians differ by at most 7.1% (local_call), all other rows
within 3.6%.

Why +10% one-sided. Same policy as the frontend floor: a speedup of any size
passes; a regression beyond +10% on a trustworthy (spread <= 12%) measurement is
a stop-and-decide signal. The in-session A/A noise (<= 7.1%) sits inside the
band. Process-spawn timings carry a load-dependent tail; criterion rows whose
std-dev exceeds 12% of the median are graded INCONCLUSIVE, never as a pass.
These values come from the build host, not from a hosted runner: the T2 and
reference commands, measured earlier the same day on the same host under lighter
load, were 18-25% faster on every row (MIND and reference alike), so a cross-machine comparison against this
floor is a backstop, not a precision instrument. Re-record it on the build host,
never from a hosted runner.
